# 指标平台按需核实本体字段的 StarRocks 类型

2026-11-24 · 已通过评审 · 归属 Metric Platform

## 要解决的问题

管理者把生产订单明细的 `product_id` 关联到商品的 `product_id` 时，希望知道这两个字段在当前数仓中是否存在、类型能否关联。当前 `OntologyBindingService` 只从固定构建的模型资源读取 `columns[*].data_type`。在 `prod` 的构建 `bae818c9-0fec-42f6-9d19-94535109a22a` 中，订单明细的该字段没有声明类型，物理列为 `bigint(20)`。图版本 39 有 13 个对象、64 个属性、21 条关系，其中 63 个属性和全部关系因 `TYPE_UNKNOWN` 显示“未核实”。

本期让平台后端在本体建模和复核时读取物理列元数据。类型核实回答“在什么时间、哪个物理表里观察到了什么类型”。主键唯一性、关系基数需要其他证据。指标计算、表达式维度的输出类型、业务行扫描和历史物理表还原均在本期范围之外。

## 方案取舍与边界

| 方案 | 能解决的问题与代价 |
| --- | --- |
| **指标平台按需直查（本次选择）** | 创建对象即可核实当前表，部署后可以再次观察。平台需要面向 StarRocks 的 JDBC 驱动、网络通路和独立的只读凭据。 |
| dbt-service 在构建时采集并封存类型 | 历史构建的证据可复现，需要扩展引擎产物和服务契约，后续物理表变化要通过新的观察发现。 |
| 仅维护 YAML 类型声明 | 可以表达模型作者的预期，需要逐列维护，单凭声明无法发现仓库中实际类型漂移。 |

前序讨论已确定由指标平台直查。本稿提出的首期范围是 StarRocks 的内部 `default_catalog`，覆盖当前本地 prod。其他适配器和外部 catalog 继续沿用声明类型的校验路径，界面标明证据来自模型声明。dbt-service 提供活动部署、构建快照和原生资源；凭据解析、元数据查询、证据存储和本体 API 改动归属指标平台。

## 物理表定位与查询

1. 复用租户管理者鉴权。服务端从环境、当前部署和已登记资产解析 `assetId → buildId → dbt model unique_id`，按该构建的执行快照确定实例和 catalog。活动部署缺失、存在歧义或资产归属不符时沿用现有错误，终止查询。
2. 使用固定构建模型资源中的最终 `schema` 和 `alias`。例如订单资源的 `database=null`、`schema=env_prod`、`alias=orders`，catalog 来自快照。允许 dbt 的表别名和已授权的自定义 schema。部署方按租户、实例和 catalog/schema 配置可访问范围，默认限定为环境快照的 schema。定位缺项或冲突时报告无法定位。浏览器只提交环境、资产和构建 ID。
3. 平台在部署配置中按可信实例选择服务端 JDBC 地址和只读元数据身份。容器必须使用平台自己可达的地址；dbt 执行快照中的回环地址在平台容器有不同含义。凭据由平台的 secret 配置注入，与构建写入账号分开维护。驱动连接、查询和读取均有超时并及时释放资源。浏览器、日志、图数据和错误详情只接收业务所需的类型或原因码。
4. 每次观察只读取一张表的元数据。在已确定的内部 catalog 中，参数化查询 `information_schema.columns`，按 `TABLE_SCHEMA` 和 `TABLE_NAME` 精确过滤，读取 `COLUMN_NAME`、`COLUMN_TYPE`。保留完整类型，如 `decimal(18,2)`。候选属性仍取自已部署模型声明的列；内部计算列不会因出现在物理表中而自动成为本体资产。
5. 身份权限要能区分“成功读取此表列清单”和“没有可见元数据”。表可见且清单完整时才能认定某列缺失；零行、权限不足或目标不可见均记录为未核实，避免误报整张表的绑定损坏。

## 用户操作与证据生命周期

| 操作 | 行为 |
| --- | --- |
| 选择数据集 | 读取该表全部列一次，展示模型声明、仓库实测类型及核实时间。端点沿用现有 `datasets/{assetId}/columns?buildId=…`。 |
| 创建、改绑属性或关系 | 服务端使用同一核实逻辑，每次保存对同一物理表最多查询一次。客户端传来的类型仅供展示。确定缺列或类型冲突时拒绝新增该绑定。临时故障下，仍可按现有规则保存已声明且无已知冲突的绑定，状态为“未核实”。 |
| 打开拓扑 | 复用同租户、同环境、同构建、同图版本的有效报告，展示观察时间。缺少有效报告时，按数据集分组重新核实。 |
| 部署切换、手动重新核实 | 下次读取新部署时重新核实，旧构建的成功证据只作历史参考。管理者可以主动刷新同一部署的证据，发现手工 DDL。一次操作查询每个涉及的数据集至多一次。 |

属性保留原有 `declaredType` 含义。另存最后一次成功观察到的物理类型、观察时间、构建 ID 和物理表定位，以及此次核实的结果和原因。首次确认的物理类型作为该属性的比较基准；后续观察先与基准比较，再保存本次结果。发生冲突时保留原基准，管理者显式重新绑定后建立新基准。属性重新绑定到不同列或数据集时，旧证据随旧绑定失效。

对于同一列有意进行的类型迁移，建议在属性详情提供“接受当前物理类型”。复用对象更新接口，在请求中显式列出待接受的属性 ID、页面展示的旧基准与新类型，并携带 `expectedRevision` 和 `sourceBuildId`。服务端重新观察，核对当前绑定、旧基准及新值，同时检查当前模型声明（如有）与新类型兼容。核对成功后在一次图编辑中更新基准，保留对象、属性和关系 ID；普通保存、打开页面、复核报告均不能隐式接受冲突。仍与对端不兼容的关系继续显示“需要修复”。并发修改或再次漂移要求管理者重新查看实际类型。

沿用 Neo4j 对绑定和报告的持久化。现有绑定缺少观察记录时可以直接读取；旧格式报告首次读取时重新生成，即使 buildId 和图版本相同。图库图版本继续表示用户编辑；手动复核和证据刷新沿用报告写入路径，同一版本的较早观察不能覆盖较新结果。瞬时故障的报告可在下次复核重试，保留最后一次成功值与时间，前端同时标出本次失败。有效报告无需定时轮询数仓。

报告复用还要核对核实策略版本。实例开关、连接目标或授权范围变化，在配置生效后的下一次普通读取即使构建和图版本相同也应重新判定。停用后按声明生成当前状态，上次实测值仅作为带时间的历史信息；收紧授权后先重做目标授权检查。策略版本使用配置代次或非敏感配置标识，禁止将密码写入报告。

打开和保存都在查询前后核对活动构建。保存继续校验 `sourceBuildId` 和 `expectedRevision`；中途发现指针或图版本改变时丢弃本次结果，要求重新加载。外部仓库和部署指针之间没有跨系统事务，时间戳只证明观察时刻的物理状态。

## 状态、接口与展示

| 证据 | 已有绑定复核结果 |
| --- | --- |
| 公开列存在，仓库类型可读，声明及已有基准均与其兼容；首次无声明也无基准 | 属性“兼容”，显示仓库类型和时间；首次核实时建立基准。 |
| 声明、已接受基准或关系两端出现明确类型族冲突 | 对应属性或关系“需要修复”，显示冲突的两种类型。 |
| 已取得完整可见的物理列清单，绑定列缺失 | 属性及引用它的关系“需要修复”。 |
| 网络超时、缺少只读凭据、无元数据权限、表定位不确定 | “未核实”，显示原因和上次成功核实时间。 |

授权策略拒绝与读取失败分开处理。对于已启用直查的实例，若目标明确超出授权范围，平台在建立连接前停止；新建或改绑返回 HTTP 403，已有绑定保留并标为“未核实／目标未授权”。临时故障的降级仅适用于已通过目标授权的绑定。明确停用直查的实例回到声明校验；已启用但意外缺少凭据的实例显示“未核实”。

关系复核汇总两个端点的证据，“需要修复”优先于“未核实”。比较继续采用现有 `BindingEvidence.compareTypes` 的类型族规则，例如 `BIGINT` 与 `VARCHAR` 冲突。同族的精度、长度变化保留完整值用于展示；状态“兼容”表示当前类型规则允许此绑定。物理表存在、Manifest 未声明的列继续遵循当前 `COLUMN_UNDECLARED` 规则。

更新 `api/openapi.yaml` 的本体列及绑定报告契约，新增可空的物理类型、来源、时间和可区分的失败原因。已有字段及三种顶层状态保持向后兼容。建议给拓扑读取增加可选的显式复核参数，默认读取行为适配已有客户端。页面在属性详情呈现声明值、实测值及时间，关系详情展示两个端点的类型；普通图节点继续使用现有状态标签。

## 验收

- 在真实 StarRocks 中验证未声明的 BIGINT 列、带精度的 DECIMAL、别名表和空表。空表也能返回正确类型。没有业务行扫描，复核一张表的多列或多条边只读取一次该表的列清单。
- 从旧格式的图版本 39 和缓存报告升级。若基线 prod 的模型和物理结构与核对时一致，13 个对象、64 个属性、21 条关系及其 ID 保持稳定；63 个原来缺少声明类型的属性及 21 条关系均可通过实测完成类型核实。
- 模拟物理列删除、类型族冲突、权限不足与超时。逐项校验表可见性、绑定状态、保存结果和历史证据。恢复连接后主动复核可恢复状态。
- 同一列合法迁移后普通保存不能覆写原基准。显式接受新类型须通过实际类型与声明检查，属性和关系 ID 保持稳定。已有边与对端发生冲突时继续报修。超出授权范围的新绑定返回 403，验证未发出 JDBC 请求。
- 验证跨租户资产、未授权 schema、外部 catalog、并发编辑、核实期间切换部署，以及两个复核结果乱序返回。检查现有只读用户的鉴权和普通业务查询。
- 发布时先配置只读身份并验证平台容器连通性，再开启该实例的物理核实。停用直查可回到声明校验，已有对象、关系和已记录证据继续保留。

实现阶段确定 JDBC 驱动版本、超时数值、内部存储字段命名和批量复核并发上限。验收以实际查询次数、状态迁移、租户边界和 OpenAPI 兼容性为准。
