# 执行环境内的业务本体维护

2026-11-20 · 已确认。本文记录业务建模与存储的本轮决定，取代早期调研稿中随 dbt 项目定义、随构建发布本体的建议。

## 产品行为

管理者进入“测试环境”，选取该环境已部署的订单数据集，定义“订单”对象、订单编号和买家编号。再创建“客户”对象，用“下单客户”关系把订单的买家编号指向客户编号。管理者可以为同一对对象再定义“收货人”。生产环境可拥有同名对象及不同字段映射。用户在测试环境编辑、删除或重新绑定，生产环境的对象和关系均独立存在。

本期交付对象、属性和关系的增删改查，环境内的拓扑展示，以及数据集和字段绑定的健康检查。每次保存单独生效。实例行、指标执行、外部调用方协议、草稿审核、历史本体浏览留在本期范围之外。dbt-service 仍是构建和部署的唯一权威，全程使用其现有公开 HTTP 接口。

## 方案取舍

已选共享图库。每个租户的每个环境拥有独立逻辑范围。独立物理图库有利于按环境迁移或恢复，但每次环境开通都会带来额外的运维工作。当前需求通过环境内的操作入口、候选过滤和服务端归属校验就能满足。另一种 PostgreSQL 主存、图库同步的方式适合需要一套关系型本体主数据的产品，本项目只需要一份可编辑的本体。图数据库是定义、绑定和拓扑的唯一存储，PostgreSQL 沿用现有租户、账号、执行环境和数据集资产登记。

建议采用 Neo4j 和官方 Java Driver，引入一项独立运行依赖。开发环境增加持久卷、连接配置和就绪检查；生产上线前对图库做一次备份恢复演练。图库故障只影响本体功能，页面明确展示暂时不可用。使用图事务提交有关联的写入，并对作用域内的稳定 ID 建立唯一性约束。可信身份和非空归属由应用写入口保证。[Java Driver 事务](https://neo4j.com/docs/java-manual/current/transactions/) · [复合唯一约束](https://neo4j.com/docs/cypher-manual/current/schema/constraints/create-constraints/)

## 图模型与写入规则

| 元素 | 身份和必要字段 |
| --- | --- |
| 环境范围 | tenantId、environmentId，组合唯一。环境是否存在、当前账号能否管理由原平台判断 |
| 对象类型 | 稳定 objectId、业务名称、说明、稳定 datasetAssetId、主键属性 ID。首版每个类型绑定一个数据集、声明一个主键属性 |
| 属性 | 稳定 propertyId、业务名称、绑定列、可获得的声明类型。属性有唯一所属对象；主键、关系两端均引用属性 ID |
| 具名业务边 | relationId、业务名称、说明、方向、声明基数、源属性 ID、目标属性 ID。固定图边类型，业务名称作为属性。两个端点各自属于同一范围 |

所有对象、属性和业务边均携带租户和环境，所有操作均限定两者。名称可改，ID 保持稳定。基数描述由管理者声明，仅依据元数据能核实的部分显示验证结果。首版支持单字段映射的一对一、多对一和一对多；具有业务属性的多对多联系可建为中间对象。对象新增及其主键属性一次提交。删除被引用的对象或属性、移除主键或改变被关系引用属性的绑定时，返回引用清单，用户先处理相应关系或在一次对象编辑中指定合法的新主键。删除边只删除所选关系。

建议按环境用一个递增的编辑序号处理多窗口并发。写事务锁定环境范围，核对调用方所见序号，校验端点、字段引用及删除依赖，然后修改并递增序号。并发冲突提示刷新，防止旧窗口覆盖或误删。该序号只用于并发控制。绑定复核另记检查依据，不能覆盖更新后的用户编辑。

## 用户操作路径和权限

1. 从现有执行环境详情进入“本体建模”。顶部持续显示环境名，对象、属性和关系均在此上下文操作。首版沿用租户唯一管理者维护规则，对只读账号关闭建模入口及对应管理 API；以后外部拓扑读取单独定义授权。
2. 新建对象先选当前环境已部署数据集，再选可声明的列作为属性，指定主键。关系表单只列本图中的对象，选择端点后只列其属性。环境选择不出现在对象或关系表单中。拓扑使用有方向、有业务名称的边，点选可编辑；对象和关系列表提供同样的操作。
3. 切换环境时卸载旧编辑器；尚未提交的输入允许用户放弃或留在原环境。清空选中节点、候选和缓存，对迟到响应核对环境再绘制。浏览器不传租户归属，后端从已认证账号取得租户，用路径环境校验管理权限，并重新限定候选和端点。即使直接提交其他环境的 ID 也无法连线。
4. 新建时没有有效部署，显示“此环境尚无可绑定的数据集”。已维护的图仍能打开；待修复属性列出原字段及原因，支持管理者重选映射。删除按钮展示受影响引用，避免隐式级联。

## 建模绑定和重新校验

长期锚点使用平台已登记的数据集资产 ID，字段绑定使用模型详情中的声明列名。构建内的节点标识由当前资产成员定位。复用既有租户环境和构建归属检查，按该环境登记的部署目标与服务活动指针核对，核对成功后读取固定构建的资源详情。持久化的检查信息包含依据的 buildId、绑定编辑序号和逐项结果。它既不属于业务身份，也不要求保留旧产物。[平台构建与授权](../../../README.md) · [平台部署核对](../../../backend/metric-app/src/main/java/com/metricplatform/catalog/DeployedAssets.java)

界面打开、刷新或保存绑定时先检查当前部署；可复用当前构建、同一编辑序号的检查结果。首版选择按需复核，避免额外的跨库同步任务。新构建中的同一资产及声明列仍兼容即可沿用。已有完整列清单能证实列缺失、明确类型冲突或资产匹配歧义时提示修复。元数据缺失、上游超时或无法证明粒度、主键唯一性时标明未核实；不要将空的列描述当作物理删列。首版只允许从公开元数据中可识别的列建立新绑定。结构兼容无法证明业务含义未变，数据集换义需要维护人确认。

保存字段更改时带上候选来源的 buildId，提交前重新核对活动构建；已切换即提示重新选取。图库与部署系统分别提交，仍可能在最后一次核对后切换：检查记录固定到原构建，下次访问一旦发现不匹配就重新核验。服务出错时保留定义。新建或改绑无法核实的引用时保留表单并停止提交，纯名称、说明或删除操作不依赖上游在线。

**两类修复的判定。** 如果现有 HTTP 输出没有证明模型列清单完整的标志，已绑定列从声明中消失仅显示“未核实：当前构建未声明该列”。只在取得明确完整性证据时标为“需修复：绑定列已移除”。验收分别使用部分声明和可证实完整的元数据样例，均只影响相关属性和关系。同一资产内改列与整对象换数据集都算显式改绑。后者可保留 objectId，但须逐项重选主键及属性映射；任何引用该对象的业务边尚存时，拒绝整对象换绑并列出相关边。这样可防止同名字段把关系静默转向另一份业务数据。

创建关系时逐项区分证据：两端属性和绑定列必须能唯一定位；已知类型明显不兼容则拒绝保存；列均存在但类型缺失时允许保存，显示“类型未核实”。关系基数、主键唯一性以管理者声明记录，缺少数据验证时界面不展示为已验证。

## 开发拆分与验收

| 交付 | 开发内容 | 验收 |
| --- | --- | --- |
| 1 · 图存储和环境入口 | metric-core 定义对象、属性、关系和存储端口；metric-persistence 增加 Neo4j 适配与可重复执行的约束初始化；metric-app 复用现有鉴权。提供环境内拓扑读取 | 真实图库验证两个租户、同租户两个环境使用同名对象时完全隔离；跨范围访问失败；图存储不可用不影响原有目录 |
| 2 · 建模闭环 | 在环境详情增加入口；实现对象、属性、关系维护与候选筛选。拟议平台路由位于 `/api/dbt/environments/{environmentId}/ontology`，根路径读取图，`/objects`、`/relations` 创建，按资源 ID 编辑删除，属性随对象原子保存。实施时补全 OpenAPI、调用端和错误契约 | 测试环境创建订单、客户、下单客户和收货人，生产图保持原值；修改显示名保留边；删除有引用的属性返回冲突；双窗口只允许一次基于同一序号的写入 |
| 3 · 部署复核与上线 | 复用现有 HTTP 适配读取固定版本元数据；展示明确的修复位置；验证图备份恢复 | 新增无关列后关系继续可用，删列只标记受影响绑定；旧产物不可读仍可修复；环境切换后旧请求不能覆盖新图；备份恢复后对象、边及绑定一致 |

建议维护端点区分未认证、权限不足、作用域内资源不存在、并发或引用冲突、绑定不合法、上游不可用。测试覆盖前端交互和直接 API 调用两条路径。数据库选型、单列键、管理端权限、按需复核和环境级并发控制是本方案的工程建议，具体实现排期在设计确认后按以上三个可验收交付拆分。
